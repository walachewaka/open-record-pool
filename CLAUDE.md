# CLAUDE.md — open-record-pool

Agent guide for working on this project. Read this first, then `README.md`, `INSTALL.md`, and `CONTRIBUTING.md`.

**open-record-pool** is a self-hosted "record pool": it scans a mounted music directory, extracts MP3 tag metadata into PostgreSQL, and serves a library UI with search, in-browser sample playback, and downloads, behind cookie-based login.

## Stack

| Layer | Tech | Notes |
|---|---|---|
| Backend | FastAPI 0.79, Tortoise ORM 0.19, aerich 0.6.3, mutagen, arq (Redis job queue), librosa/numpy + ffmpeg/fpcalc (MOO-87 analyzer) | Python 3.11 (`python:3.11-slim-bookworm`); pydantic stays v1 / FastAPI < 0.100 / aerich 0.6.x with `.sql` migrations until the dedicated modernization issue (see `docs/ARCHITECTURE.md`). Source in `backend/src`; keep it 3.7-syntax-compatible (the harness venv is 3.7) and never import arq at module level outside the worker entry points `src/worker.py` / `src/worker_heavy.py`; numpy/librosa are imported lazily inside worker-job function bodies only (`src/analysis/engine.py`). |
| Frontend | Vue 3.5, vue-router 4, vuex 4 (+ vuex-persistedstate), @vue/cli 5 / webpack 5, axios | Source in `frontend/src`. Docker build stage uses node 16; keep `package-lock.json` at lockfile version 2 so that build keeps working. |
| Database | PostgreSQL (compose service `db`, internal-only, no published port) | Adminer with auto-login on http://127.0.0.1:8087. |
| Serving | NGINX serves the production frontend build (multi-stage `frontend/Dockerfile`, SPA history fallback) | No source volume mounts in prod; dev-server mount exists only as a documented override in `docker-compose.override.example.yml`. |
| Orchestration | Docker Compose (`docker-compose.yml`: `frontend`, `backend`, `worker` (arq consumer), `redis` (internal-only, no published port), `db`, `adminer`); single-image variant via root `Dockerfile` + `docker-compose.singleimage.yml` (inline jobs, no redis) | All published ports bind `127.0.0.1` only — keep it that way (GH #36). |

Repo layout: `backend/` (FastAPI app: `src/auth`, `src/crud`, `src/routes`, `src/schemas`, `src/database`, `src/extract`, plus `migrations/`, `docker-entrypoint.sh`, `wait_for_db.py`), `frontend/` (Vue app + `nginx.conf`), `adminer/`, `docs/`, `sh_*.sh` helper scripts.

## Running the stack

```bash
docker compose up -d --build   # start; DB migrations run automatically on boot
docker compose ps              # status
docker compose logs -f backend # logs
docker compose down            # stop, KEEP database + music volume
docker compose down -v         # stop and WIPE the database (admin bootstrap resets too)
```

URLs: frontend http://localhost:8088 · backend http://localhost:5000 (Swagger at `/docs`) · Adminer http://localhost:8087.

Single all-in-one image (GH #26 — NGINX + uvicorn under supervisord, built locally, never pushed to a registry):

```bash
docker build -t open-record-pool:local .
docker compose -f docker-compose.singleimage.yml up -d --build   # frontend on :8090
docker compose -f docker-compose.singleimage.yml down -v
```

`down -v` semantics matter: it deletes the Postgres volume, so the users table empties and the next `/register` must re-bootstrap the admin (see Auth below). Plain `down` preserves everything.

## Auth semantics

- Cookie-based: `POST /login` sets an `Authorization` cookie (JWT, httponly, SameSite=Lax). All `/notes` and `/songs` endpoints require it; unauthenticated → `401 {"detail": "Not authenticated"}`. Errors are always `{"detail": "..."}`.
- **Sessions & hardening (MOO-89):** JWTs are signed with PyJWT (HS256) and carry a `jti` backed by the server-side `auth_sessions` table, so sessions are revocable — `POST /logout` (this session), `POST /logout-all`, per-session `GET/DELETE /users/me/sessions[...]`, and admin `GET/DELETE /admin/users/{id}/sessions` all take effect immediately. Idle timeout = token lifetime (`ACCESS_TOKEN_EXPIRE_MINUTES`, default 30, silently rotated while active via `SessionCookieMiddleware`); absolute cap = `SESSION_ABSOLUTE_HOURS` (12). Passwords use argon2id (`src/auth/users.pwd_context`), with legacy bcrypt hashes upgraded on the next login. `ORP_ENV=production` refuses dev/default secrets at boot (`src/security/prodcheck.py`); `COOKIE_SECURE` controls the Secure flag + HSTS. Reusable helpers for downstream issues live in `src/security/*`: `ratelimit.rate_limit`, `authz.ensure_owner_or_403`, `paths.safe_join`, `audit.audit_event`, plus the `SecurityHeaders`/`OriginCheck` middlewares and the startup route guard.
- The frontend uses axios `withCredentials` plus an interceptor that surfaces backend `detail` messages — keep both when touching HTTP code. SameSite=Lax means plain `<a href>` downloads and `<audio>` streaming from localhost:8088 → localhost:5000 work without extra attributes (same-site; ports are ignored).
- **Registration is admin-gated** via the `ADMIN_USERNAME` env var (set to `admin` in `docker-compose.yml`):
  - Empty users table → the **first** `/register` must use username `ADMIN_USERNAME` (bootstrap; demo stack uses `admin` / `admin123`).
  - Afterwards only the logged-in admin can `POST /register` new users; anyone else gets `403`. Duplicate username → `409 Conflict` (not 401 — GH #43/#35).
  - `ADMIN_USERNAME` unset/empty → open registration (legacy behavior).
- **Single sign-on (MOO-88):** OIDC providers (Entra ID, Google, Google Workspace, Okta, …) are **environment config, not code** — `OIDC_PROVIDERS=<ids>` plus an `OIDC_<ID>_*` block each (issuer, client id/secret, scopes, provisioning policy, allowed domains, optional group→role map); the registry is parsed at import and fails the boot on half-configured providers. Client secrets never touch the DB. Flow: `GET /auth/methods` (public; what the gate renders) → `GET /auth/oidc/{provider_id}/start` (PKCE S256 + state + nonce in a signed, 10-min `oidc_txn` cookie; `?link=1` links to the signed-in account) → `GET /auth/oidc/{provider_id}/callback` (RS256-only ID-token verification against the cached JWKS, issuer/aud/nonce checked, then **a normal MOO-89 `auth_sessions` session** — one session system, no provider token stored). Those three paths are the only additions to `PUBLIC_ROUTES`. Failures redirect to `/login?sso_error=<code>` with a coarse enum (`denied|expired|invalid|not_permitted|pending_approval|domain_not_allowed|already_linked|rate_limited`). Accounts: one user, N `user_identities`, matched **only** on `(provider, subject)` — never by email; `OIDC_EMAIL_AUTOLINK` (default off) is the sole exception and needs a verified, unambiguous email. Provisioning is **default-closed per provider** (`closed|invite|domain|open`) and never creates or claims `ADMIN_USERNAME` — the admin registration gate is untouched. Self-service `GET/DELETE /users/me/identities[/{id}]` and admin `GET /admin/sso/providers` (site_settings), `GET/DELETE /admin/users/{id}/identities[/{id}]` (manage_users); unlinking the last sign-in method → `409`. `LOCAL_LOGIN_ENABLED=false` makes the pool IDP-only (`/login` → 403; boot refused if no provider is configured). Rate buckets `idp_start`/`idp_callback` (10/min/IP); audit events `auth.sso.login`, `auth.sso.login_failure`, `user.sso_provisioned`, `user.identity.linked`, `user.identity.unlinked`. Logout is local-only (the IDP session survives). Operator guide: `docs/SSO.md`.
- **Upgrade-path lock-out caveat (GH #41):** on an *existing, non-empty* DB with no user named `ADMIN_USERNAME`, nobody can ever create accounts — bootstrap only fires on an empty users table. Workaround (documented in `INSTALL.md`): set `ADMIN_USERNAME` to an existing username, or set it empty to disable gating, via a compose override. Don't "fix" this by weakening the gate.

## Song / extraction API contract (GH #5, #9, #6, #10, #11, #13)

All require the auth cookie. The frontend `/library` view is built against exactly this contract — don't change shapes without updating both sides.

- `POST /songs/extract` — **changed by MOO-77**: requires the `site_settings` permission (an instance-wide mutation) and enqueues the scan as a background job. Response: `202` with the job envelope (`{"id", "kind", "status", "queue", "progress", "payload", "result", "error", "created_by_id", "created_at", "started_at", "finished_at"}`); in inline mode (`WORKERS_ENABLED=false`) the job is already terminal with `result` set to the old shape `{"files_parsed", "duplicates_skipped", "songs_created", "songs_updated", "songs_deleted", "songs_total"}`. A scan already queued/running → `409`. The scan itself is incremental: files whose size+mtime match the stored row are skipped without being read.
- `GET /admin/jobs` (view_reports; keyset-paginated `id DESC`, filters `status`/`kind`) and `GET /admin/jobs/{id}` (view_reports OR the job's creator — the Browse rescan polls this) — background job list/detail (MOO-77).
- **`GET /search` (MOO-79)** — the ES-backed instant-search surface the Search view uses (the legacy `/songs` contract is untouched). Params: `q` (≤200 chars, MOO-69 key/BPM semantics), repeatable `genre`, `year_min/max`, `bpm_min/max`, `key`, `bitrate_min`, `source` (library|upload), `sort` (relevance|added_at|title|artist|bpm|year), `order`, `limit` (1–100), `cursor` (ES search_after keyset). Response: `items` (SongOutSchema shape + the extended ID3 fields), `next_cursor`, `total`+`total_relation` (`gte` when capped at 10 000), `took_ms`, `degraded`, and combinable `facets` whose counts exclude their own dimension. Only published tracks. Rate limited 20/5 s per user → `429`. ES down/disabled → identical filters through the PG path with `degraded: true` — never a 5xx. Sync contract: **every song write path must enqueue a `search_outbox` row + nudge** (see `docs/ARCHITECTURE.md` § Search); `GET /admin/search/status` (site_settings) shows doc parity/outbox backlog; `POST /admin/settings/reindex` (site_settings, 202 job envelope, rate limited 3/60 s) rebuilds ES from PG with zero downtime.
- `GET /healthz` — public (the only unauthenticated route): `{"status", "database", "redis"}`; `redis` is `null` in inline mode; DB failure → `503 "degraded"`.
- `GET /songs` — paginated list + search. Params: `q` (free text over title/artist/album/genre, case-insensitive; a key-shaped query like `8A`/`Am` additionally matches every notation of that musical key and a numeric query matches songs whose BPM rounds to it — MOO-69, feeds the Search view), `page` (≥1), `page_size` (1–300, default 50), `sort` (whitelist: `id, title, artist, album, genre, year, bpm, duration_seconds, created_at` + aggregate sorts `most_downloaded, most_played, genre_title` (MOO-65); anything else → `422`; `musical_key` is deliberately NOT sortable), `order` (`asc`/`desc`). Extended filters (MOO-65, additive): `bpm_min`/`bpm_max`, `key` (Camelot like `8A` or raw notation like `Am` — matches every notation mapping to the same Camelot code), `genre` (repeatable, case-insensitive multi-select). Items carry `id, title, artist, album, genre, year, track_number, bpm, musical_key, duration_seconds, bitrate_kbps, file_size_bytes, created_at` + `camelot_key` (best-effort derived, nullable) and `is_favorite` (per current user) (MOO-65); every tag field is nullable. **Since MOO-87** `bpm`/`musical_key`/`camelot_key` serialize the COALESCEd tag-then-detected values (tag always wins, analyzer fills gaps) and the BPM/key filters, key/BPM-shaped `q`, and `sort=bpm` match on the same coalesced expressions; new item fields `bpm_detected`, `key_detected`, `waveform_ready` expose analyzer provenance. **Cursor mode (MOO-77)**: passing `cursor` and/or `limit` (1–100) switches to keyset pagination — `sort` must be `id` or `created_at` (else 422), the response carries `next_cursor` (null on the last page) and `total: null`. Offset mode is unchanged but capped: `page * page_size > 10000` → 422.
- `GET /songs/genres` — distinct genres present in the library, sorted alphabetically (MOO-66, feeds the Browse genre chips). Declared before `/songs/{id}` so the literal path isn't shadowed by the int param.
- `GET /songs/genres/stats` — `[{genre, track_count}]`, alphabetical (MOO-69, feeds the Genres view tiles).
- `GET /songs/{id}` — release detail (MOO-65): listing fields + `download_count`, `play_count`, `tags[]` (genre/album/year chips), `versions[]` (today a single `Original / MP3` entry with `stream_url`/`download_url`; shape ready for future versions/WAV). Since MOO-87 also `bpm_mismatch`/`key_mismatch` (nullable; set when the file's tags disagree with the audio analysis — half/double-time BPM and enharmonic keys are NOT mismatches).
- **`GET /songs/{id}/waveform` (MOO-87)** — the analyzed waveform peaks: `{"song_id", "version": 1, "algorithm", "count": 1000, "duration_seconds", "peaks": [0..1 floats]}`; `ETag` = file checksum + `Cache-Control: private` (304 on `If-None-Match`); 404 until analysis produced it (frontend falls back to seeded bars). Same published-only visibility as `/stream`.
- **`GET /songs/{id}/analysis` (MOO-87)** — the full `track_analysis` serialization (statuses, technical facts, detected BPM/key + confidence, mismatch flags, LUFS/LRA/true peak, cue in/out, fingerprint columns, quality flags); returns the all-null "pending" shape before analysis ran; `tags_json` only for callers with `edit_metadata`.
- **`POST /admin/analysis/backfill` (MOO-87)** — `site_settings`; body `{"force"?, "fields"?}` (unknown field → 422); 202 job envelope (`analyze_library`); 409 while one is queued/running; rate limited 3/300 s; audited as `analysis.backfill_started`.
- **`GET /admin/analysis/stats` (MOO-87)** — `view_reports`; analyzer coverage + heavy-queue depth/throughput (feeds MOO-83).
- `GET /songs/{id}/stream` — chunked `audio/mpeg`, `Accept-Ranges: bytes`, single-range `Range` → `206`, unsatisfiable → `416`. Used as the `src` of the persistent `<audio>` player.
- `GET /songs/{id}/download` — attachment, `Content-Disposition: attachment; filename*=utf-8''Artist%20-%20Title.mp3`. Records the download in the user's history and enforces the monthly quota → `429` when exhausted (MOO-65); re-downloading a song the user already downloaded never counts against quota. Optional `format` param (only `mp3` today, else `422`).
- Duplicate key (GH #9): normalized artist + title (case/whitespace-insensitive) + duration rounded to the nearest second; files missing artist or title fall back to MD5 checksum. First file in path order wins.

## CRATE member API (MOO-65)

All require the auth cookie; errors are `{"detail": "..."}`. The Camelot helper lives in `backend/src/utils/camelot.py` (never raises; returns null on unknown notations).

- **Crates (playlists, MOO-84 extended)**: `POST /crates` `{name, color?, description?}` · `GET /crates` (mine, with `track_count`) · `GET /crates/public?q=&cursor=&limit=` (browse/search everyone's public crates, keyset `id DESC`, never a private crate or a `share_token`) · `GET /crates/{id}` (owner, `public=true`, platform owner/admin, or via share link; detail = summary + `owner_id`, `owner_username`, `total_duration_seconds`, first-200 `tracks[] {position, song}` + `tracks_next_cursor`) · `GET /crates/{id}/tracks?cursor=&limit=` (keyset `(position, id)` page of the full membership) · `PATCH /crates/{id}` `{name?, color?, description?, public?}` (visibility toggle audits `crate.visibility_changed`) · `DELETE /crates/{id}` · `POST /crates/{id}/duplicate` `{name?}` (copies any crate the caller can read into a fresh private crate they own; rate-limited) · `POST/GET/DELETE /crates/{id}/cover` (JPEG/PNG, <=2 MiB, content-addressed under `/library/art`) · `POST /crates/{id}/share/rotate` (new `share_token`; old link 404s) · `POST /crates/{id}/tracks` `{song_id}` (appends at a gap-based position, step 1000; dup → `409`) · `PUT /crates/{id}/tracks` `{song_ids}` (full-permutation reorder, capped at 1000 tracks → else `422`; use the move endpoint above that) · `PATCH /crates/{id}/tracks/{song_id}` `{after_song_id}` (single-track DnD move; midpoint position, rebalances on gap collapse) · `DELETE /crates/{id}/tracks/{song_id}` · `GET /crates/shared/{share_token}` (read via share link, even if private) · `GET /crates/{id}/export.m3u` (`#EXTM3U`, entries point at download URLs, batched). Crate create/update also take `dj_target` (`serato|traktor|rekordbox|null`, MOO-86) and every crate response carries it. `share_token` is only exposed to the owner; mutation is owner-only (`403`), except platform Owner. Read access also allows platform `owner`/`admin` roles on private crates (write stays owner-only).
- **Favorites**: `POST /songs/{id}/favorite` (toggle → `{song_id, is_favorite}`) · `GET /favorites` (paginated song page, newest favorite first).
- **Play events**: `POST /songs/{id}/play` → `{song_id, play_count}` — call when playback starts; feeds Most played.
- **Downloads**: `GET /downloads` (paginated history, newest first; items carry `format`, `counted_against_quota`, `downloaded_at`, `song`) · `GET /downloads/quota` → `{limit, used, remaining, unlimited, month}`. Quota is per user per calendar month (UTC), configured by the `DOWNLOAD_QUOTA_MONTHLY` env var (compose sets 100; `<= 0` = unlimited).
- **Charts**: `GET /charts?mode=most_downloaded|most_played|added_this_month&limit=N` → `{mode, entries[] {rank, metric, song}}`; metric = download count / play count / days since added. Zero-count songs are omitted from the downloaded/played modes.

## CRATE admin API (MOO-71)

Backend for the admin console. All require the auth cookie **and** a role permission; missing permission → `403`. The admin console UI (next stage) is built against exactly these shapes.

- **Roles & permissions.** Every user has a `role` (owner/admin/curator/member), plus informational `plan` (free/pro/crew) and account `status` (active/suspended/pending/invited). The `ADMIN_USERNAME` account is promoted to **Owner** on every boot (`promote_admin_to_owner`, a startup hook) — this layers on the bootstrap gating, does not replace it. Owner has every permission, locked on. Permission keys (matrix rows): `browse_download, create_crates, upload_tracks, edit_metadata, approve_submissions, manage_users, manage_roles, site_settings, view_reports, manage_billing`. Coded defaults in `src/auth/permissions.py`; overrides persist in `role_permissions`. `require_permission("<key>")` is the FastAPI dependency guarding every admin route.
  - `GET /admin/roles` (manage_roles) — full matrix. `PUT /admin/roles/{role}` (manage_roles) — overwrite one non-owner role; Owner → `403`.
- **Users** (manage_users): `GET /admin/users?q=&role=&plan=&status=&page=&page_size=` · `POST /admin/users` (invite/create; `owner` role not assignable) · `GET /admin/users/{id}` · `PATCH /admin/users/{id}` (role/plan/status/profile — suspend/reinstate here; the Owner cannot be demoted/suspended/deleted) · `DELETE /admin/users/{id}`. **Suspended users cannot log in or use any API** (enforced in `get_current_user` + `/login`).
- **Content & moderation**: songs gained `status` (published/draft/pending/rejected). **Member listings only ever surface published tracks** (`/songs`, genres, charts, favorites). `GET /admin/content?q=&status=` (edit_metadata) · `PATCH /admin/content/{id}/status` (edit_metadata, publish/draft toggle) · `PATCH /admin/content/{id}` (edit_metadata, DB-only tag edit — never rewrites files) · `GET /admin/moderation` (approve_submissions, pending queue) · `POST /admin/content/{id}/approve|reject` (approve_submissions) · `POST /admin/content/upload` (upload_tracks, multipart).
- **Settings** (site_settings): `GET/PUT /admin/settings` (grouped general/library/storage/integrations KV in `instance_settings`; unknown keys → `422`) · `POST /admin/settings/scan` (**MOO-77**: enqueues the `/music` extraction as a job, `202` job envelope, `409` when one is already pending; the task records the last-scan summary) · `POST /admin/settings/reindex` (**MOO-79**: real zero-downtime ES reindex job, `202` envelope, `503` when search is unconfigured/down in inline mode). `general.public_signup` is stored-only and deliberately does NOT open registration (would weaken the admin gate).
- **Dashboard/reports** (view_reports): `GET /admin/stats/dashboard` (stat cards, real `shutil.disk_usage` storage %, 14-day series, top genres/tracks, downloads-by-format, needs-attention pending count, system-health flags) · `GET /admin/stats/reports?start=&end=&limit=` (date-range aggregates).

## Ingestion analyzer (MOO-87)

Full design in `docs/ARCHITECTURE.md` § Ingestion analyzer. The essentials:

- **Two tiers**: pass 1 (mutagen technical facts + full tag dump, runs inside scan/upload, `src/analysis/technical.py`) and pass 2 (job `analyze_track` on queue `orp:heavy`, consumed by the `worker-heavy` compose service): waveform peaks, decoded-PCM sha256, spectral cutoff, EBU R128 loudness, silence cue points, BPM/key (librosa), Chromaprint fingerprint. Results live in `track_analysis` (one row per song) with per-field `field_versions` provenance; `src/analysis/versions.py` holds the constants — bump ONE to make only that pass stale.
- **Dispatch seam**: every ingestion path calls `src.analysis.dispatch.enqueue_analysis(song_id)` (deduped per song). Backfill = job `analyze_library` on `orp:default`, throttled to `ANALYZE_BACKFILL_WINDOW` in-flight jobs.
- **Precedence**: tag bpm/key always win; detected values only fill gaps (COALESCE everywhere a song is serialized/filtered/sorted, expression-indexed). Never overwrite `songs.bpm`/`musical_key` from the analyzer (tag writes are MOO-82's).
- **Scaling env** (worker-heavy): `WORKER_HEAVY_CONCURRENCY` (default derived from cpu_count, logged at startup), `ANALYZER_NICE=10`, `ANALYZER_MAX_MEM_MB=512`, `OMP_NUM_THREADS=1`/`NUMBA_NUM_THREADS=1`; scale out with `--scale worker-heavy=N`. Binaries via `FFMPEG_PATH`/`FPCALC_PATH` (apt: `ffmpeg`, `libchromaprint-tools`, `libsndfile1`).
- **Waveform artifact** at `/library/waveform/<aa>/<bb>/<checksum_sha256>.json` (`{"version":1,"algorithm":"ffmpeg-pcm-max","count":1000,"duration_seconds",peaks[0..1]}`), written via `storage.store_artifact_bytes`; the frontend (`utils/waveform.js` `fetchPeaks`/`peaksToBars`) renders it in TrackRow/PlayerBar/Release with the seeded bars as universal fallback (Charts tiles stay decorative/seeded on purpose).
- **Testing**: harness tests NEVER shell out to ffmpeg/fpcalc or import numpy — monkeypatch the five `src.analysis.engine` seam functions (`decode_and_measure`, `loudness_and_silence`, `bpm_and_key`, `fingerprint`, `file_sha256`); see `../harness_analysis.py`.

## Duplicates & recordings (MOO-90)

- **Model:** `recordings` is the dedup unit — one row per specific mix/edit (normalized artist/title/mix, duration, external IDs: ISRC/MusicBrainz/Beatport/Spotify, `canonical_song_id`). Each `songs` row is one *version* of a recording (`songs.recording_id`, nullable — a Recordings row is created lazily when a second version appears or an external ID is learned). `songs.version_status` ∈ `canonical | superseded | quarantined | pending_review`. **An extended mix and a radio edit are different recordings and are never merged.**
- **Match cascade** (`src/services/dedup.py`, cheapest first): L1 byte hash (`checksum_sha256`, md5 fallback) → L2 decoded-PCM hash (`track_analysis.pcm_sha256`) → L3 chromaprint similarity over the local `fingerprint_ngrams` index (never O(n)) → **L4 duration guard** (fingerprint match + duration delta > `library.dedup_duration_tolerance_seconds` = related cut, NOT a duplicate → `recording_links`) → L5 metadata corroboration (adjusts confidence; alone it is review-queue evidence at most, never an auto-merge). Certain (L1/L2) auto-resolves; confident fingerprint matches auto-resolve unless `library.dedup_auto_resolve_fingerprint=false`; borderline/conflicting → `duplicate_candidates` pending review.
- **Quality ranking** (`src/services/quality.py`): lexicographic tuple — format class, *effective* bitrate (spectral-cutoff-capped: a "320" with a 16 kHz shelf ranks as its true quality; declared bitrate is never trusted alone), sample rate, not-suspect, integrity (decode_ok + no clipping), source trust (`library.dedup_source_trust`), file size. Equal tuples keep the incumbent.
- **Nothing is ever deleted or moved by dedup** — flag-only version statuses (same rule as the read-only `/music`); losing versions stay as rows, restorable via `POST /admin/recordings/{id}/promote`. Every decision emits a `dedup.*` audit event.
- **Member surfaces filter to `version_status="canonical"`** on top of `status="published"` (`filter_songs`, genres/stats, charts, favorites, ES query). Member `GET /songs/{id}` on a non-canonical version → 404; admins get it with `canonical_song_id` for redirect. Admin content exposes `version_status`/`recording_id`.
- **Pipeline:** analysis completion (`tasks_analysis._analyze_song`) enqueues `dedup_song` on `orp:heavy`; `POST /admin/duplicates/backfill` (site_settings, dry-run default writes `proposed` rows only) runs the retro walker. Admin surface: `GET/POST /admin/duplicates*` (edit_metadata), review UI at `/admin/duplicates`.
- **Downstream contracts (MOO-78/81/85):** `POST /library/check` + `src/services/dedup.py::check_library(...)` (pre-download skip / `would_improve`), `evaluate_incoming(song_id, claimed)` (post-download decision; claimed-vs-audio mismatch → `mismatch_quarantined`, never merged), `attach_external_ids(recording_id, ...)` (ID conflicts raise review candidates). Harness: `../harness_duplicates.py`.

## Download engine (MOO-78)

Fetch tracks from a public provider URL into the library via pinned CLI tools (yt-dlp / scdl / spotDL) running as subprocesses in isolated venvs (`/opt/tools/*`, never imported into the app). Full operator doc: `docs/DOWNLOADS.md`.

- **Providers ship DISABLED** — per-provider toggles in Admin → Settings → Integrations (`integrations.downloads_enabled` + `downloads_{youtube,soundcloud,spotify}`, `downloads_require_approval`, `downloads_daily_limit`; all default off/20). `songs.source` now ∈ `library | upload | youtube | soundcloud | spotify`; `songs.source_url` holds the canonical provider URL.
- **Model:** `download_requests` = one row per acquisition attempt-series. States: `queued → fetching → postprocessing → imported | duplicate_skipped | failed | cancelled`. Every request also gets a `jobs` row (`kind="fetch_track"`, queue `orp:heavy`, on `worker-heavy`). Migration 12.
- **Routes** (all authz-declared): `POST /fetch` (perm `upload_tracks`, rate-limited 10/60s + daily quota, 202), `GET /fetch` (own, keyset), `GET /fetch/providers` (UI gate + tool versions), `GET /fetch/{id}` (owner or `view_reports`), `POST /fetch/{id}/cancel|retry` (owner or `approve_submissions`), `GET /admin/fetch` (`view_reports`). Submission returns `503` when `WORKERS_ENABLED=false` (downloads require the worker tier; test-only inline via `DOWNLOADS_INLINE_OK=true`).
- **Pipeline** (`src/downloads/pipeline.py`): probe → MOO-90 `check_library` pre-fetch skip → fetch → tag-normalize (title/artist from source metadata, `TXXX:ORP_SOURCE_URL`) → `storage.store_stream` (sha256 sharded `/library`) → `Songs.create` → `outbox` (ES) → `dispatch.enqueue_analysis` (auto-chains dedup). Mirrors `crud.content.upload_track`. sha256 or `dedup_key` collision → `duplicate_skipped`.
- **SSRF guard** (`src/security/urlcheck.py`, SECURITY.md item 9): https-only, exact-host allowlist (no suffix match), IP-literal reject, resolved-IP private/loopback/link-local/CGNAT/metadata reject, single-track canonicalization (playlists → 422). Tools invoked argv-only (never a shell string), scrubbed env, private workdir, hard timeout.
- **Downstream contract (MOO-81/80):** `src.downloads.service.enqueue_download(url, requested_by_id, origin, origin_ref, priority, enforce_user_policy)` + `DownloadPolicyError`/`DuplicateActiveRequest` + `register_completion_hook(origin, cb)`. System callers pass `enforce_user_policy=False` (skips rate-limit/quota, never the URL/enable gates); MOO-81 origin `"request"`, MOO-80 `"artist_follow"`.
- **Tool pins** in `backend/tools/*.txt` → per-tool venvs in the Dockerfile; **refresh monthly** (a stale yt-dlp = provider outage, not a security event). Optional creds are env-only + redacted: `SPOTIFY_CLIENT_ID/SECRET`, `SOUNDCLOUD_AUTH_TOKEN`, `YTDLP_COOKIES_FILE`. Mock adapter for e2e: `ORP_FAKE_DOWNLOADS=true` handles the fixture URL `…watch?v=ORPFIXTURE1`.

## Song requests (MOO-81)

Members ask for a track missing from the library; a request is moderated (or auto-approved) then fulfilled through the MOO-78 download engine. Full plan: see the MOO-81 issue comment history — this section is the durable summary for downstream stages (MOO-85 enrichment, artist-follow auto-request, a future Discord notification channel).

- **Capability caveat (read this before touching fulfillment):** `src.downloads.service.enqueue_download` only ever fetches from a provider **URL** — there is no query-search entry point (no spotDL/yt-dlp search wrapper anywhere in the codebase). Free-text requests therefore **cannot** be auto-fulfilled from an artist/title alone: auto-approve only ever applies to `kind="url"` requests. A free-text request always lands `pending`; a moderator supplies a `source_url` in the `POST /admin/requests/{id}/approve` body to fulfill it (also usable to gap-fill a `url`-kind request, though it normally already has one).
- **Model:** `song_requests` (migration 14). `kind` ∈ `free_text | url`. Lifecycle `pending → approved → downloading → fulfilled`; terminal exits `duplicate | rejected | failed | cancelled`. `download_id` is a **soft, un-FK'd** reference to `download_requests.id` (D3.4: decoupled by design, never breaks if that table's shape moves under it).
- **Fulfillment linkage:** on approval, `src.crud.song_requests._enqueue_fulfillment` calls `enqueue_download(url, requested_by_id, origin="request", origin_ref=str(request.id), enforce_user_policy=False)`. `downloading → fulfilled/failed` propagates back via `sync_requests_from_downloads()`, run both as **read-repair** (top of every list/summary/detail read, scoped to the rows being shown) and as a **60s worker cron** (`sync_song_requests_cron`, registered in `src/worker.py`) — covers the no-page-open case and `WORKERS_ENABLED=false` inline mode alike.
- **Dedup:** `src.services.dedup.check_library(artist=, title=, mix=)` runs at submission for `free_text` requests only (a `url` request carries no parsed metadata pre-fetch). `match_layer="external_id"`, or `"fingerprint"` at/above `library.dedup_fingerprint_threshold`, is treated as `"certain"` → the request is created `status="duplicate"` with `duplicate_of` pointing at the existing song; anything else `check_library` finds is `"likely"` → the request proceeds `pending` with `possible_duplicate_of` set (surfaced to the moderator as a warning, never blocking).
- **Settings** (`instance_settings` group `song_requests`, in `src/crud/settings.py` `DEFAULT_SETTINGS`): `enabled` (bool, default true — 403s submission when off), `auto_approve_roles` (list, default `[]`; owner is implicitly auto-approved), `daily_quota` (int, default 5, UTC day, 0 = unlimited; counts every created row incl. duplicates/cancelled).
- **Routes** (all authz-declared): `POST /requests`, `GET /requests/mine`, `GET /requests/mine/summary`, `POST /requests/mine/seen`, `GET /requests/{id}` (owner or `approve_submissions`, 404 on foreign id — IDOR-safe), `POST /requests/{id}/cancel` (owner-only, from `pending` only) — all `get_current_user`. Admin (`approve_submissions`): `GET /admin/requests`, `GET /admin/requests/stats`, `POST /admin/requests/{id}/approve|reject|retry`, `POST /admin/requests/bulk`.
- **Frontend:** member `/requests` (`views/Requests.vue`, sidebar badge = `unseen_resolved`), admin `/admin/requests` (`views/admin/AdminSongRequests.vue`, sidebar badge = pending count via `admin/requests/stats`), settings card under Admin → Settings → Requests. Vuex: `store/modules/song_requests.js` (member) + `admin.js` (`requestsPendingCount`).
- **Audit events** (`src/security/audit.py`): `song_request.created|auto_approved|approved|rejected|retried|cancelled|fulfilled|failed`.

## Beatport metadata enrichment (MOO-85)

Beatport is an optional metadata-enrichment source: search-and-match against the Beatport API v4 catalog, fill genre/label/year gaps, and surface BPM/key/ISRC/catalog-number/remixers/artwork for a future consumer (MOO-82's ID3 editor). This stage never writes an audio file or downloads artwork — it only writes to the DB and serves the data over the admin API.

- **Operator setup (real credentials).** Beatport API v4 access requires an **approved partner application** — apply at https://api.beatport.com/v4/docs/ before you have real `BEATPORT_CLIENT_ID`/`BEATPORT_CLIENT_SECRET` values; this is a real operational blocker, not a config step you can skip. Until that application is approved, run in **mock mode** (below) to evaluate and use the whole feature with zero network/credentials.
- **Env vars** (all optional; every one has a safe default and the feature degrades cleanly with none set): `BEATPORT_MOCK` (default false — `true` swaps in the deterministic fixture client, `src/enrichment/mock_client.py`), `BEATPORT_ENABLED` (`false` forces "disabled" even with credentials present), `BEATPORT_CLIENT_ID` / `BEATPORT_CLIENT_SECRET` (env-only, never logged, never stored), `BEATPORT_API_BASE` (default `https://api.beatport.com/v4`), `BEATPORT_RATE_LIMIT_RPS` (default 2), `BEATPORT_CACHE_TTL_HOURS` (default 720 = 30 days), `BEATPORT_BACKFILL_BUDGET_PER_HOUR` (default 3600 — spreads the library-wide backfill's API calls across an hour), `BEATPORT_TIMEOUT_SECONDS` (default 15), `BEATPORT_AUTO_APPLY_THRESHOLD` / `BEATPORT_REVIEW_THRESHOLD` (default 0.85 / 0.60 — the scoring gates below). Flipping mock off and setting real credentials is a pure env-var change: zero code edits.
- **Provider tri-state** (`src/enrichment/provider.py::provider_status()`, never calls Beatport itself): `mock` (fixtures), `live` (creds present, not disabled), or `disabled` with a machine-readable `reason` (`credentials_not_configured` | `disabled_by_env`). `GET /admin/enrichment/status` always works; the trigger routes return a clean `503` when disabled — never a 500.
- **Outbound policy** (`src/enrichment/beatport_client.py`): hard host-allowlist to the configured API host, `follow_redirects=False` (a redirect response is an error), a request timeout, and an asyncio token-bucket rate limiter shared across every call one client instance makes. Artwork URLs are only ever stored if `https` and the host is `beatport.com` or a subdomain. Every GET is a Postgres read-through cache (`beatport_cache`, keyed by `sha1(method+url+params)`, migration 16) — not Redis (MOO-77 declared Redis wipeable transport; cached responses must survive a restart at library scale).
- **Matching** (`src/enrichment/normalize.py` + `scoring.py`, pure stdlib `difflib.SequenceMatcher`, no new dependency): normalizes artist/title, splits a mix name out of a trailing `(... mix word ...)` group (default `"original mix"`), and computes a weighted composite score across title(.30)/mix(.10)/artist(.25)/duration(.20)/bpm(.075)/key(.075), renormalizing over whatever signals are actually present on both sides. Classification: `applied` (score ≥ `BEATPORT_AUTO_APPLY_THRESHOLD` **and** title ≥ 0.90 **and** artist ≥ 0.85 **and** duration delta ≤ 5s), `needs_review` (score ≥ `BEATPORT_REVIEW_THRESHOLD`), else `no_match`.
- **Storage & field-lock precedence (binding): `manual` > `beatport` > file tag.** `songs.field_locks` is a `{field: "manual"|"beatport"}` JSON map. `sync_songs_from_disk` (the `/music` rescan, `src/crud/songs.py`) now **skips any field present in `field_locks`** when comparing/updating from file tags — this is the fix for the MOO-71/72 quirk ("DB edits are silently reverted by the next scan"), scoped to owned fields only. `src/crud/content.py::edit_metadata` sets `field_locks[field] = "manual"` for every field it changes, so manual admin edits now survive rescans too and always outrank a Beatport apply. Auto-written fields on apply/accept are exactly **genre, label, year** — `songs.beatport_track_id` is denormalized for fast lookups. Everything else (bpm, key, isrc, catalog_number, release_name, release_date, artwork_url, remixers, subgenre) lives only in the `song_enrichment.payload` JSON, served via the API (below) for a future consumer to read — Beatport's bpm/key are **cross-check only** (`payload.bpm_mismatch`/`key_mismatch` booleans), never overwriting the analyzer's detected values (MOO-87 owns those). Un-apply restores the pre-apply snapshot and clears the `beatport` locks (a `manual` lock is untouched either way).
- **Model:** `song_enrichment` (one row per song+provider, migration 16) carries `status` (`pending|applied|needs_review|no_match|rejected|error`), `match_method` (`auto|manual`), `confidence`, the normalized `payload`, the top-5 scored `candidates` (each with its own component-score breakdown and full candidate payload, so accepting a match never re-calls Beatport), `fields_applied`, and `tag_snapshot`. `beatport_cache` is the response cache (above).
- **Jobs** (arq, queue `orp:heavy`, `src/jobs/tasks_enrichment.py`): `enrich_song` (single-song pipeline), `enrich_library` (resumable backfill — keyset-walks `songs.id` from a persisted cursor, budget-throttled to `BEATPORT_BACKFILL_BUDGET_PER_HOUR` calls/hour, skips `applied`/`rejected` rows unless `force`), `enrichment_manual_search` (reviewer-driven re-search). Instance setting `integrations.beatport_auto_enrich` (default off, `src/crud/settings.py`) auto-enqueues `enrich_song` for every song a library scan or admin upload creates/updates, when the provider is enabled.
- **Admin API** (`/admin/enrichment/*`, `src/routes/admin_enrichment.py`, gated by the existing `edit_metadata` permission — no new permission key): `GET /status` (never calls Beatport); `POST /songs/{song_id}` (202 job envelope, rate-limited 30/60s, 409 if already queued, 503 if disabled); `GET /songs/{song_id}` — **the stable contract MOO-82's ID3 editor consumes** for suggested values + artwork candidates, keep this shape stable; `POST /backfill` (202, rate-limited 3/hour, 409 if already running); `GET /queue` (keyset-paginated review queue, filter by `status`); `POST /{enrichment_id}/accept` (body: optional `beatport_track_id` + `fields` subset; never calls Beatport — 422 on an unknown candidate id, "run manual search first"); `POST /{enrichment_id}/reject`; `POST /{enrichment_id}/unapply`; `POST /{enrichment_id}/manual-search` (202 job envelope). All mutating actions are `audit_event`-logged (`enrichment.applied|rejected|unapplied|backfill_started`).
- **Downstream contracts:** `src.enrichment.service.get_external_ids(song_id) -> {"beatport_track_id", "isrc"}` for MOO-90's cross-source validator; an apply also best-effort attaches `beatport_id`/`isrc` onto the song's `recordings` row via `src.services.dedup.attach_external_ids` (guarded, never raises, never auto-merges a conflicting id). Every apply/un-apply/reject best-effort re-syncs the MOO-79 search outbox.
- **Mock mode** (`BEATPORT_MOCK=true`): `src/enrichment/mock_client.py` ships four deterministic fixtures exercising every match outcome — an exact match (auto-applies), a duration-mismatched same-title/artist candidate (lands `needs_review`, never auto-applied), a wrong-artist decoy (`no_match`), and a metadata-rich track (catalog number, ISRC, remixers, artwork) for the review UI. The whole feature — search, scoring, review, apply/un-apply, rescan survival — is exercisable end-to-end with zero network/credentials.
- **Frontend:** `/admin/enrichment` (`views/admin/AdminEnrichment.vue`, `edit_metadata`, sidebar entry under Duplicates): provider status card (mode badge, disabled reason, counts, cache size), a backfill trigger, a keyset-paginated review queue (SegmentedControl by status), and a detail drawer (candidate cards with per-component scores + artwork, a genre/label/year checklist respecting locks, accept/reject/un-apply, manual search). The auto-enrich-on-import toggle lives on the existing Admin → Settings → Integrations tab (`beatport_auto_enrich`).

## Metadata editor & album art (MOO-82)

The full ID3 editor. **Database-side only:** an edit changes the pool's metadata, never the file's bytes — `/music` is read-only, and writing tags back into MP3s is MOO-75 (blocked on the owner's writable-volume decision). What makes an edit durable regardless is MOO-85's field-lock mechanism, so nothing here needs a writable mount.

- **Editable set** (`EDITABLE_FIELDS`, `src/crud/tags.py`): title, artist, album, album_artist, composer, genre, label, comment, isrc, year, track_number, disc_number, bpm, musical_key, and the custom TXXX frames (`songs.txxx_frames`, ≤32 entries, desc ≤64 chars, value ≤512 — the same caps extraction applies). Validation lives in `ContentMetadataUpdateSchema` (ISRC regex, BPM 20–999, year 1000–2100). `songs.isrc` (TSRC) is new and is read by extraction.
- **One write path.** Every edit — admin PATCH, batch, approved proposal, rollback — goes through `crud.tags.apply_changes` → `crud.content.write_metadata` (sets values, re-normalizes artist/title, locks the touched fields `"manual"`, re-indexes via the MOO-79 outbox) and records a `tag_revisions` row. A field outside `EDITABLE_FIELDS` is a 422 — a proposal can never reach `status`, `file_path`, …
- **History & rollback** (`tag_revisions`, append-only): `{field: {old, new}}` per edit, with the editor's username denormalized so history survives account deletion. Rollback applies the inverse as a NEW revision; it 409s when the track changed since (an undo must not silently discard a newer edit). Batch members share a `batch_id` and can be undone as a unit.
- **Batch edit** is restricted to release-level fields (artist, album, album_artist, genre, label, year, comment — `BATCH_FIELDS` in `src/schemas/tags.py`), ≤1000 ids, one row at a time so per-song locks/history/re-index still happen.
- **Album art** (`src/utils/artwork.py`): every image — upload, Beatport candidate, or the file's embedded APIC — is sniffed by **magic bytes** (never extension/Content-Type), capped (`ART_MAX_UPLOAD_MB`, default 10), decoded under a 50 MP bomb guard, and **always re-encoded** (strips EXIF/smuggled payloads) to an RGB JPEG ≤1400px, stored content-addressed under `/library/art` via `storage.store_artifact_bytes`. `songs.artwork_path/_source/_width/_height` point at that display copy; `songs.has_artwork` still means "the file carries an APIC". Served by `GET /songs/{id}/artwork` behind the same auth as the track (never a static mount). A candidate URL is fetched **only** when Beatport already gave us that URL for that song (allowlist by construction — SSRF, SECURITY.md item 9).
- **Suggestions** are read off MOO-85's stored `song_enrichment.payload` (`GET /admin/content/{id}/suggestions`); applying one is an ordinary PATCH, so it locks the field and lands in the history like any other edit. MOO-85's own auto-apply set (genre/label/year) is unchanged.
- **Permissions:** `edit_metadata` writes directly (no new permission key). Members **propose** (`POST /songs/{id}/tag-proposals`, rate-limited 10/hour, one pending proposal per track) and a curator approves/rejects from Moderation → Tag suggestions; approval replays the proposal through the normal pipeline, crediting the revision to the proposer and the audit event to the reviewer.
- **API:** `PATCH /admin/content/{id}` (now the full field set), `GET /admin/content/{id}/revisions`, `POST /admin/content/{id}/revisions/{rid}/rollback`, `POST /admin/content/tags/batch`, `POST /admin/content/batches/{batch_id}/rollback`, `GET|PUT|DELETE /admin/content/{id}/artwork[/candidates|/select]`, `GET /admin/content/{id}/suggestions`, `GET /admin/tag-proposals`, `POST /admin/tag-proposals/{id}/approve|reject`, `GET /songs/{id}/artwork`, `POST /songs/{id}/tag-proposals`, `GET /users/me/tag-proposals` (`src/routes/admin_tags.py`, `src/routes/tags.py`).
- **Frontend:** the Admin → Content edit drawer is now a four-tab editor (Fields | Artwork | Suggestions | History) with a multi-select batch bar; Moderation gains a "Tag suggestions" tab; Release renders the real cover and offers "Suggest an edit". New dependency: `Pillow==12.2.0`.

## Artist follows & release tracking (MOO-80)

Users follow artists; a poll tick tracks upcoming/new releases against a release source (Sonarr/Radarr concept) and matches them to the library.

- **Capability caveat (read this before touching D2/D6 below):** the plan for this stage assumed both a Beatport `search_artists`/`get_artist_releases` endpoint and a query-based `enqueue_download`. Neither exists in the shipped code:
  - MOO-85's client (`src/enrichment/beatport_client.py`) only exposes `search_tracks(query)`/`get_track(id)` — no artist-id or artist-releases endpoint. `src/sources/beatport.py` approximates both by querying track search and grouping by release; a Beatport "artist" external id is `sha1(name_norm)` (no numeric id is available).
  - `src.downloads.service.enqueue_download` only ever fetches from a resolved provider URL (same caveat as MOO-81, see above) — there is still no search-by-query entry point. So "grab" and "auto-grab" here create a **free-text song request** (`src.crud.song_requests.create_request`, `kind="free_text"`) for each unmatched track — the issue's own stated alternative ("auto-create a song request") — rather than an instant download; a moderator supplies a `source_url` to fulfill it like any other free-text request.
- **Model** (migration 18): `artists` (materialized from the library — one row per normalized name via `src.utils.normalize.normalize_artist`, `track_count`, `beatport_artist_id`, reserved `musicbrainz_id`, poll bookkeeping), `artist_follows` (per-user `user ↔ artist`, `settings` JSONB `{auto_grab, notify}`, unique `(user, artist)` — follows dedupe onto one artist row so poll cost never grows with user count), `releases` (shared/global — one poll, one row, one library state for everyone; unique `(source, external_id)`; `status` ∈ `missing | in_library | grabbed | ignored`, sticky: `ignored` never auto-reverts, `grabbed` only flips to `in_library` on a later full match), `follow_feed_state` (per-user "seen" marker for the sidebar badge).
- **Release source abstraction** (`src/sources/`): `ReleaseSource` (`base.py`) with `configured()`/`search_artists(q)`/`get_artist_releases(external_artist_id, since, artist_name=None)`; `BeatportReleaseSource` (adapter above); `MockReleaseSource` (`RELEASE_SOURCE_MOCK=true`, default false — deterministic fixtures, `source="mock"` so it never collides with real data); `registry.get_release_sources()` returns `[mock]` if mock is on, else `[beatport]` if configured, else `[]` (the degraded no-source path — follows/list/detail routes stay 200, `GET /artists/search` returns `external: [], sources_configured: false`, the poll job returns `{"skipped": ...}`; never a 5xx). MusicBrainz slots in later behind one more file + one registry line.

## DJ crate export — Serato / Traktor / rekordbox (MOO-86)

A crate (playlist) is exported as a **USB-ready ZIP** whose internal layout is what the target software expects at the ROOT of a stick. The server never sees the stick, so ZIP-download is the delivery; the user extracts it at the drive root.

- **Bundle layout** (all three share `Music/NN Artist - Title.ext`, position-prefixed so file managers keep the order): Serato adds `_Serato_/Subcrates/<Crate>.crate` (scanned automatically off any attached drive — no import step); Traktor adds `<Crate>.nml`; rekordbox adds `rekordbox.xml` (the documented Preferences → Advanced → Database → rekordbox xml import path — a native `PIONEER/` .pdb device DB is deliberately out of scope: undocumented binary, corruption risk on CDJs). Every bundle carries `EXPORT_README.txt`.
- **Portability:** Serato `ptrk` paths are drive-root-relative (works on any drive letter/mount). Traktor addresses volume + `/:`-separated dir, so the export takes a `volume_label` (default `ORP_USB`; README tells the user to name the stick that, or right-click → Relocate once). rekordbox `Location` URIs are absolute, so it takes `rekordbox_root` (default `/Volumes/<label>`; Windows users pass a drive like `E:`).
- **Writers** (`src/export/`, all pure + unit-tested, no new dependency): `serato.py` (the reverse-engineered TLV stream — 4-byte tag + BE uint32 length + UTF-16BE payload; we never write `database V2`, Serato rebuilds it), `traktor.py` (NML v19 via ElementTree; `PRIMARYKEY` must byte-match `LOCATION` volume+dir+file or the playlist imports greyed out; `BITRATE` is bits/s), `rekordbox.py` (DJ_PLAYLISTS 1.0.0; playlist `<TRACK Key>` references `TrackID`), `naming.py` (sanitized, deduped, non-escaping arcnames), `tagging.py`, `bundle.py`.
- **Key notation** (`src/utils/keys.py`): one 24-row table on top of `utils/camelot.py` — `key_forms(raw)` → `{camelot, standard, open_key, traktor_int}` (never raises). Serato gets Camelot in `TKEY`, Traktor Open Key + its 0–23 int, rekordbox standard `Tonality`.
- **Metadata:** tags are rewritten (mutagen) on the **bundled COPY only** — `/music` is read-only and file-tag writeback is still MOO-75's. Title/artist/album/genre/year/track + `TBPM`/`TKEY` come from the DB (tag value wins, MOO-87 analyzer fills gaps). Frames we do not set are untouched, so existing Serato `GEOB` cue/beatgrid frames survive. **Beatgrids/cues/waveforms are NOT generated** — the DJ software analyzes on first load; stated in the README, the modal, and this file.
- **Pipeline** (`jobs/tasks_export.py`, `kind="export_crate"`, queue `orp:default`, MOO-77 jobs row + `JobOut` envelope): per track — resolve the source against the three served roots (outside/missing → recorded in `result.skipped`, never fatal unless all fail), copy chunked into `/library/tmp/export-<job_id>`, retag, stream into the ZIP (`ZIP_STORED` — MP3 does not deflate), delete. **Peak scratch = one track**, so a 40 GB crate needs no 40 GB temp. Artifacts land at `/library/export/<job_id>/<Crate>_<fmt>.zip`; the `cleanup_exports` cron (30 min) drops bundles past `EXPORT_TTL_HOURS` and orphaned staging dirs, and download then returns `410`.
- **Routes:** `POST /crates/{id}/export` `{format?, volume_label?, rekordbox_root?}` → `202` `JobOut` (read access = crate read access; `format` defaults to `crate.dj_target`, absent both → `422`; empty crate / over `EXPORT_MAX_TRACKS` → `422`; ≥2 active exports per user → `409`; rate-limited 10/h → `429`). `GET /exports/{job_id}` (poll; result = `{download_url, bundle_filename, zip_size_bytes, track_count, skipped[], expires_at}`) and `GET /exports/{job_id}/download` (`FileResponse`; path recomputed from the job id, never client input). Both are creator-or-owner only — **no signed/unauthenticated artifact URLs**; the SameSite=Lax cookie already makes a plain `<a download>` work same-site. Audits `export.requested` / `export.downloaded`.
- **Env vars:** `EXPORT_TTL_HOURS` (24), `EXPORT_MAX_TRACKS` (1000).
- **Frontend:** `components/ExportDjModal.vue` (target radio cards preselected from `dj_target`, volume label, rekordbox root, size estimate + >4 GiB exFAT warning, progress bar, download link) behind CrateView's "Export for DJ" button; `utils/exports.js`. `Release.vue`'s single-track "Send to DJ" stays a stub (needs a local bridge that does not exist) — its toast now points at crate export.
- **Not machine-verifiable here:** no DJ hardware/software in this environment. `qa/harness_export.py` validates structurally (round-trip-parses its own `.crate`, asserts the NML/XML contracts, unzips each bundle, checks tags on the copies) — a human still has to open each bundle from a real stick.

## Telemetry & Grafana dashboards (MOO-83)

Every interesting thing that happens becomes an Elasticsearch document, and four provisioned Grafana dashboards read them back inside the admin panel. **PostgreSQL stays authoritative for everything that matters** (play/download rows, the audit log, quota); telemetry is a strictly additive, best-effort projection — losing it costs nothing.

- **Emission** (`src/telemetry/emitter.py`): `emit(event, **fields)` is a synchronous dict-build + `deque` append. No network, no Redis, no await. A background asyncio task in each process (API, worker, worker-heavy) bulk-ships batches to `orp-events-YYYY.MM` every `TELEMETRY_FLUSH_INTERVAL_SECONDS`. **Nothing here can raise into a request path**: emit swallows, the flush loop swallows, a dead ES requeues the batch and warns at most once a minute, and a full buffer drops its OLDEST events and counts them (`events_dropped`). ES down ⇒ the app is completely unaffected.
- **Taxonomy** (`src/telemetry/events.py` — use these helpers, never raw `emit`): `play.start`, `play.complete` / `play.skip` (from the beacon), `download`, `search.query`, `import.track`, `enrichment.applied`, `export.crate`, `request.created|approved|rejected|fulfilled`, `job.finished`, `api.request` (sampled), `auth.login` + `audit.*` (shipped from PG). Common envelope: `@timestamp`, `event`, `user_id`, `username`, `hour_of_day`, `day_of_week`; `song_label` ("Artist - Title") is precomputed so a top-tracks panel is one terms agg. Unmapped kwargs land under the flattened `attrs` — the index mapping is `dynamic: false` and can never explode.
- **Consent** (`TELEMETRY_LEVEL`): `off` (≡ disabled) | `basic` (no `api.request`, and `search.query` keeps counts but drops the raw query string) | `detailed` (default). Telemetry is also automatically off wherever `ELASTICSEARCH_URL` is unset, which is what keeps the single-image build and ES-less environments untouched.
- **job.finished** comes from `src/jobs/instrumented.py`, which wraps each task at the one boundary both execution modes share (the arq registry and `submit_job`'s inline dict) — task bodies are untouched, and a new task is instrumented by being registered.
- **Audit → ES** (`src/telemetry/shipper.py`): a 60s arq cron (inline mode: the flush loop) copies new `audit_log` rows in, keyed `_id="audit-<row id>"` so it is idempotent, with the cursor recovered from a `max(audit_id)` agg in ES. **No new PG state, no migration.**
- **Retention:** ILM policy `orp-events-retention` deletes an index `TELEMETRY_RETENTION_DAYS` (default 180) after creation. Monthly indices age from creation, so effective raw retention is 180–210 days.
- **Grafana** is **never published — not even on 127.0.0.1** (`expose:` only). With `auth.proxy` on, anything that can reach port 3000 can impersonate any user via `X-WEBAUTH-USER`. The one way in is `ANY /admin/grafana/{path}` (`src/routes/grafana_proxy.py`): gated on `require_permission("view_reports")`, it strips every client-supplied `X-WEBAUTH-*` header, never forwards the ORP cookie, and injects the caller's identity (`Admin` for owner, else `Viewer`). Dashboards are code (`docker/grafana/dashboards/*.json`, uids `orp-listening|orp-library|orp-engagement|orp-system`) with a provisioned ES datasource; UI edits are disabled.
- **Frontend:** `/admin/insights` (`views/admin/AdminTelemetry.vue`) — status chips + the dashboards in an iframe pointed at OUR origin's proxy path. `PlayerBar.vue` POSTs `telemetry/beacon` on `ended` and on any track change mid-play; the backend classifies ≥85% (or `ended`) as `play.complete`, else `play.skip`. Two security middlewares know about the prefix: `security/headers.py` swaps `X-Frame-Options: DENY` for `frame-ancestors 'self' <ALLOW_ORIGINS>` there, and `security/csrf.py` also accepts same-origin POSTs (the embedded Grafana JS posts to `/admin/grafana/api/ds/query` with the backend's own Origin).
- **Routes:** `POST /telemetry/beacon` (member, rate-limited 120/min, always 202 — a beacon must never error the player or leak which song ids exist), `GET /admin/telemetry/status` (`view_reports`; ES/Grafana reachability, buffer, counters, shipper lag), `GET /admin/telemetry/config` (`site_settings`).
- **Env:** `TELEMETRY_ENABLED` (true), `TELEMETRY_LEVEL` (detailed), `TELEMETRY_BUFFER_MAX` (5000), `TELEMETRY_FLUSH_INTERVAL_SECONDS` (2), `TELEMETRY_FLUSH_MAX_BATCH` (500), `TELEMETRY_API_SAMPLE_RATE` (0.1 — 5xx is never sampled away), `TELEMETRY_RETENTION_DAYS` (180), `GRAFANA_URL`, `GRAFANA_ADMIN_PASSWORD` (prodcheck refuses the `grafana-dev` default in production). Full detail in `docs/TELEMETRY.md`.
